# Anchor Library: application audit and product direction

Date: 18 October 2026. Scope: the existing Next.js/Supabase application, its native PDF readers, and the highest-risk authenticated user flows. This is a functional and access-control audit, not a full penetration test, load test, or accessibility certification.

## Problems fixed

| Area | Finding | Result |
| --- | --- | --- |
| Study room counts | Persisted sessions silently rejoined outside rooms; the listing forced a minimum count of one | Presence belongs to the actual room page. Leaving, navigating away and signing out untrack it. Observers are not counted; duplicate identities are deduplicated. |
| Realtime lifecycle | The installed Supabase client reuses channels by topic; two components subscribed to the same room channel | The session provider owns the presence channel. Chat uses a separate database-change channel and authenticated message retrieval. |
| Private chat | API routes accepted client-supplied account IDs and used an elevated database client without adequate membership checks | Server-verified identity, participant checks before reads/writes, recipient-only request handling, scoped read timestamps, private/no-store responses. |
| Room broadcasts | Direct-message content could be broadcast to the public room; incoming broadcasts were trusted | Removed message broadcasts. Database changes trigger an authorised fetch; private threads do not publish their content to a room. |
| Reading privacy | Other members' profiles exposed reading history | Other-member cards return no books/progress. Current book names are no longer broadcast in presence. |
| Database boundary | Profile emails were anonymously readable; browser mutations could bypass application intentions | Included a transaction-based ACL/RLS migration for profile columns, personal records and chat participants. Direct role changes are denied; admin account actions use a verified server API. |
| Username login | An anonymous lookup endpoint returned an account email | Sign-in resolves the username on the server, returns no email/token in its JSON response, uses session cookies, and validates local redirect paths. The lookup endpoint now returns 410. |
| Favourites | Book detail control did not save anything | Authenticated save/remove API, persistent pressed state, saved shelf, navigation link and working dashboard counts. |
| Notifications | The application queried a nonexistent `read` field and inferred unread state from the last sender alone | Uses `is_read` and participant `last_read_at`; adds a working in-app bell with an honest empty state. |
| Mobile chat | CSS hid the conversation pane at every mobile width | A selected conversation displays its pane; a back control returns to the inbox. Failed sends preserve the draft. Late responses cannot populate another thread. |
| Focus session | Timer drifted when a background tab was throttled | Elapsed wall-clock seconds advance work/break phases, including several missed phases. Landing launcher carries a goal and 15/25/50 minute plan into Pomodoro. |
| Room reading | An empty subject shelf could leave Pomodoro without any reading choices | Clearly labelled general library suggestions when no room matches exist; covers use the available catalog image field. Ambient audio stops when leaving. Unknown room IDs show not-found. |
| Search/dashboard | Relation-query fallback discarded search/category filters; some totals were limited to visible rows | Filters survive fallback; delimiter input is sanitised, category URLs encoded, reading/favourite totals use exact counts. Continue Reading opens the reader. |
| Landing/UI | Fake scale claims, excess top spacing and no clear first task | Editorial reading-led landing, real catalog counts, interactive focus launcher, reading shelf, room entry points, privacy/community guide, responsive navigation. |

The reading-note test added one takeaway to the provided account's Meditations notes. Tests did not delete existing records or modify another member's role/account. Test-room tabs are left or closed before completion.

The SQL migration is separate from a Git/Vercel deployment. Its observed database access effects were verified directly; retain the migration in version control for reproducibility.

## What notifications mean today

- Pending incoming study-partner requests: open the inbox and accept or decline.
- Unread private conversations: open the specific thread; its own read timestamp clears the unread state on refresh/poll.
- Existing unread account notifications: open the dashboard and mark the stored record read.

These are in-app notifications. Browser push, email, scheduled reminders, streak alerts and AI messages are not implemented. The bell does not create artificial notifications, and account updates require an actual stored notification producer. The interface shows seven days of chat history; it does not promise automatic deletion from storage/backups. Direct messages are not end-to-end encrypted; service operators retain operational access.

## Competitor research and positioning

Primary product sources reviewed on the audit date. This is a feature comparison, not an independent performance benchmark.

| Product | Verified focus | Useful lesson for Anchor |
| --- | --- | --- |
| [Focusmate](https://www.focusmate.com/) | Scheduled 25/50/75-minute video accountability sessions, partner matching and favourite partners | Make starting a planned session effortless, and close it with a concrete takeaway. Anchor's camera-free reading room plus integrated Hindi/English library is a distinct proposed positioning. |
| [StudyStream](https://help.studystream.live/hc/help/en/categories/focus-rooms-studying) | Focus rooms, Pomodoro, streaks, presence/connection handling and small spaces; camera is optional | Honest room counts, clear session lifecycle and consensual partner interactions matter more than inflated activity metrics. Camera-free alone is not a unique competitive claim. |
| [Forest](https://www.forestapp.cc/) | Focus time represented through growing virtual trees and habits | Reward completed reading intentions and retained learning, rather than adding social noise. A reading reflection is a better first addition than a complex points economy. |

Recommended proposition: **“Read Hindi or English, focus alongside others, and keep what you learn—without needing a camera.”** This is a product hypothesis, not a proven market advantage. Validate it with actual readers and measure return rate, session completion, and notes revisited.

The current release implements the focus launcher, reading-first landing, saved shelf, privacy boundaries and reliable session presence. Suggested next releases, in order:

1. Block/report/mute controls with audited moderation workflows, database enforcement, abuse limits and a published retention policy. Required before aggressively growing public rooms.
2. Consent-based partner invitations to a shared session, availability preferences and invitation expiry. Do not expose personal reading history by default.
3. End-of-session reflection and an owner-only session history. Track verified attendance before awarding streaks; define timezone handling.
4. Review queue for saved highlights, then spaced-repetition flashcards. Keep reminders opt-in.
5. Accessibility and network-resilience pass with keyboard-only use, assistive technology, real Android/iOS devices, reconnect tests, and cold/warm PDF timing on throttled networks.

## AI implementation proposal

No AI provider or paid inference is connected in this release. Do not add a decorative chatbot that pretends to work.

Start with **“Explain this passage”** next to a selected highlight. The user chooses Hindi or English and explicitly submits the selected passage. Return a short explanation, a vocabulary hint and one self-check question; the current page/book citation is displayed separately. Generate flashcards only on request, and let the user edit before saving.

Proposed flow: selected passage and page → authenticated Next.js server route → book/access check, length/rate/budget limits → provider call → streamed answer. Keep provider credentials server-side. Send the selected passage and necessary context only; do not automatically send partner messages, full reading history or other people's notes. Treat retrieved document text as untrusted data, never executable instructions.

For later whole-book question answering, ingest only authorised/licensed books with page-labelled chunks, use retrieval constrained to allowed book IDs, and return actual supporting passages. Supabase vectors or hosted file search are implementation choices; permissions must be enforced before retrieval. [OpenAI's file-search documentation](https://developers.openai.com/api/docs/guides/tools-file-search) describes hosted retrieval and file citations. **A file citation alone is not a validated page number**: page-level references must come from ingestion metadata and be checked.

If using OpenAI Responses, configure response storage deliberately, and review [official OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data) for the selected endpoints/tools. `store: false` is not a blanket zero-retention guarantee; file/vector-store lifecycle and abuse-monitoring rules need separate review. Disclose the provider and data sent before enabling the feature.

Release only after a bilingual evaluation set checks groundedness, fabricated citations, unsupported answers, prompt injection and cross-account retrieval. Add per-user quotas and a hard project spending cap; choose the model against measured quality/latency/cost rather than a marketing label. This design remains a roadmap until provider configuration, budget and evaluation are complete.

## Remaining operational limits

- Browser-delivered PDF bytes and publicly shared Drive originals cannot be made download-proof. Watermarks, login checks and UI deterrents are not DRM. Private origin storage and short-lived authorised delivery are the next infrastructure step.
- Presence counts reflect connected accounts. Abrupt network loss can take the Realtime timeout to expire; public client presence is not authoritative proof of attendance or protection against deliberate spoofing.
- Chat request acceptance is not yet a single database transaction; add an atomic RPC and uniqueness constraints for robust concurrent accept/retry handling.
- Polling is a fallback for inbox and chat. Measure database load before increasing usage; add proper pagination and notification aggregation rather than increasing polling frequency.
- Signup confirmation-email delivery, recovery flows, actual destructive admin actions, large-scale concurrency, third-party outages and every catalog PDF were not exhaustively exercised in production.
- Profile editing is still explicitly marked Coming Soon. No claim is made that every possible feature or security issue is finished.
